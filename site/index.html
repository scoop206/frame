resume

Pick up the conversation, not just the code.

If most of your work with Claude happens in Claude Code sessions, the expensive part isn't the code. It's the context: the decisions, the dead ends, the "we tried that, it broke X".

frame shell --recent lists your latest sessions by their first message. Pick one and it resumes in the directory it ran in. Give Claude the latest update and decide where to go next.

  • --find "WORDS" searches what you typed, for when you remember what you said but not when.
  • ● marks a session that's already open. Picking it switches to that window instead of forking it.
  • --resume ID when you already know the session.

ask

Question anything on screen, from Neovim.

Reviewing what Claude wrote, or what it said? Select the lines, run :'<,'>FrameClaude with your question, and the selection (file:line plus the fenced source) lands in this frame's Claude, already submitted. Then you talk it through.

Map it to a key once and it's two keystrokes:

-- init.lua
vim.keymap.set('v', '<leader>L', ':FrameClaude ')

coordinate

One coordinator, many workers.

Start in a shell frame: a Claude in any directory, with no branch and no worktree, so by design it isn't writing code. It plans. When change needs to happen, it frame spawn wts a worktree frame in whichever frame-enabled repo needs it, sends the work over frame req, and collects the replies in its inbox.

Each worker is fully isolated: its own branch, its own Neovim, its own ports and dev servers. The coordinator keeps the big picture; the workers keep their hands off each other.

  • Turned on with spawn_frames=true in frame kv. With it off, the coordinator asks before spawning. macOS
  • If a repo already has a live frame, the coordinator finds it in frame ls and sends the work there instead.
  • frame wt TOPIC --from SRC hands a whole conversation forward to a new frame when the work changes shape.

isolate

Several agents at once, nothing colliding.

Running more than one Claude Code session on a repo usually means two dev servers fighting over a port, an agent editing main, and worktrees nobody remembers to clean up. A frame is self-contained and disposable, and delivery back to main goes through guarded steps.

frame wt TOPIC

A branch, a worktree, and assigned ports for its services. Agents work on their topic branch, never in the primary checkout.

frame merge

Refuses on a dirty primary, fast-forwards to origin first, and aborts cleanly on conflict instead of leaving a half-merge.

frame wt -d

Removes the worktree and branch, stops the dev servers it started, and reaps frame state. Nothing left running.

autonomy

You decide how far it goes on its own.

frame kv tells each frame's Claude what it may do without asking. Set it per frame, per project, or for every project. Settings can change mid-session, and agents re-check before they act.

autocommitcommit each finished, working step
merge_on_committhen frame merge it into main
push_on_mergepush main to origin after merging
deploy_on_mergeand deploy when the project knows how
spawn_framesspawn worker frames in other repos without asking

install

Four lines to a first frame.

  • zsh
  • git ≥ 2.5
  • Neovim
  • Claude Code
  • Ghostty (recommended)
  • docker (shared services only)
zsh
git clone https://github.com/scoop206/frame.git
cd frame
echo "export PATH=\"$PWD/bin:\$PATH\"" >> ~/.zshrc && source ~/.zshrc
frame --help

Then cd into a project, run frame init, and frame wt my-topic. The onboarding guide covers project types, buffers and ports.

macOS is the primary target. The core workflow (worktrees, the Neovim layout, the Claude broker, merge and teardown, ports, shared services) runs on Linux too and is tested there in CI. Window focus and frame spawn are macOS-only.
