A2A: should frames speak Agent2Agent?

verdict: done. task model shipped; protocol not adopted.

Tracked in issue #1 (closed).

frame already has agents messaging agents: a coordinator sends work with frame req and replies land in frame inbox. A2A is the open standard for exactly that kind of traffic. So should frame speak it?

What A2A is

Google announced the Agent2Agent protocol in April 2025 and gave it to the Linux Foundation that June. The first stable spec, v1.0, shipped in March 2026, and more than 150 organizations back it. The main pieces:

  • Agent Card. A JSON file an agent publishes describing its skills, its endpoint and the auth it accepts, so other agents can find it.
  • Transport. JSON-RPC 2.0 over HTTPS, with gRPC and HTTP+JSON bindings too.
  • Tasks. Every request becomes a task with an id and a lifecycle: submitted, working, input-required, auth-required, completed, failed, canceled, rejected. Results come back as messages and artifacts, streamed over SSE or pushed to a webhook.

The premise is that agents are opaque to each other. They share no memory, tools or files. A2A is built for agents that cross vendor and organization boundaries. MCP is the complementary layer: MCP connects an agent to its tools, A2A connects an agent to other agents.

How it maps onto frame

Most of A2A has a frame counterpart already.

A2Aframe
Agent Card, discoveryframe ls lists live frames; frame kv --of TOPIC shows what one is working on

Task: id, state, cancelevery request is a broker task: an id (the NAME/TOPIC#rN token frame req prints), states queued, inflight and done, and status, await and cancel calls

That last row is the interesting one. A2A covers how agents talk. It says nothing about how they're created, what codebase they share, or what a human lets them do. Those are most of what frame is.

Could frame adopt it?

Yes, as a thin bridge beside the broker: one local HTTP server that publishes an Agent Card for each live frame, turns message/send into a frame req, completes the task when the reply arrives, and reports input-required when the frame is Blocked. All the pieces exist. The new part is a long-lived HTTP server in a codebase that is otherwise zsh.

Should it, today?

Not yet, for two reasons.

  1. Nothing on the other end. Every frame runs Claude Code, and we couldn't confirm any first-party A2A support in Claude Code. A bridge would translate between frames that already understand each other.
  2. The opposite premise. A2A assumes opaque agents that don't trust each other. Frames share a filesystem, git, Neovim and a human, and that sharing is where frame's value comes from.

Security: a requirement, not a blocker

Binding to localhost or a private network keeps network attackers out. The path that remains is your browser. Any web page you visit can make your browser POST to localhost (the browser blocks the response, but the request still lands), or reach it through DNS rebinding. For a dev server that's a minor risk. For an endpoint that types prompts into a Claude running with frame yolo on, it means a web page could run shell commands on your machine.

The standard fixes are well known, and any bridge frame ships would have all of them:

  • bind to 127.0.0.1 only;
  • reject requests whose Host or Origin header isn't localhost;
  • require a token read from a file only your user can read.

What frame takes from A2A now

Less than you might expect, because the broker already has the task model. Every frame req becomes a task with an id (the NAME/TOPIC#rN token it prints) and a state: queued, inflight or done. What was missing was the sender's view of it, and that is what we took:

  1. The sender can check its own requests, with frame req status: everything it has sent and not heard back on, each with its state read live from the target.
  2. Two more states. lost, A2A's failed: the target frame died or finished without a reply, so the sender finds out in seconds instead of at a timeout. And blocked, A2A's input-required: the receiving Claude is waiting on its own human. Blocked is shown, but only as advice (see the updates below).

Both make a swarm of frames easier to follow, and both bring the broker's states closer to A2A's, so a future bridge would be mostly renaming. There is no cancel; the updates say why.

What would change the answer

  • Non-Claude agents, such as Gemini CLI or Codex, running as frame types.
  • Frames spread over several machines, which Linux support makes more likely.
  • Claude Code shipping A2A itself.

We're also watching Claude Code's own native cross-session messaging. It overlaps frame's broker more directly than A2A does.

Updates

  1. 2026-11-24 analysis

    The broker already had a task model

    This page first said frame would take A2A's task model. Reading the broker closely, it already had one: every request is a task with an id (the NAME/TOPIC#rN token), the states queued, inflight and done, and calls to await and cancel it. But only a frame's own client, frame claude, could use them. The frame that sent a frame req couldn't see what happened to it.

    The worst case: if the target frame died, or finished without any reply text, frame inbox --wait --for ran all the way to its timeout. Slow and dead looked the same.

  2. 2026-11-24 response shipped

    The sender's view: frame req status

    frame req status lists everything this frame has sent and not heard back on: queued #N, working 7m, blocked, reply on its way, in your inbox, or lost. The target's broker stays the source of truth; the sender only keeps a small outbox of what it sent.

    frame inbox --wait --for now notices a lost request within about five seconds and exits 5, and a timeout says what the target was doing. Agents learn all this from hint lines in the output (check later: frame req status <token>), not from more text loaded into every session.

    Found on the way: the "ask a sibling" recipe that frames get at session start saved all of frame req's output instead of just the token, so its wait never matched a reply and always ran to the timeout. Fixed.

  3. 2026-11-24 decision

    No cancel

    A request already in flight can't be stopped. Its answer can only be sent somewhere else, while the target keeps working. A cancel command would promise more than it does.

  4. 2026-11-24 decision

    "Blocked" is advice, not a stop

    We first made blocked end the wait early too. But the blocked status can linger after the human approves a prompt, so an agent could give up on a frame that is already working again. Clearing it properly needs a hook on every tool call, about 9ms each for a call into the frame's Neovim. With permission prompts off in practice, that cost buys little. So the wait reports blocked once and keeps waiting.

  5. 2026-11-24 open

    What is it doing right now?

    For a frame watching a sibling, the most useful next step may be a line showing what the target is doing at this moment, such as its latest tool call. Not built yet.

  6. 2026-11-25 closed

    Spike closed

    Closed: spike done, outcome shipped. Tracked in issue #1.
